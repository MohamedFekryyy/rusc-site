# rūsc booking server: Cal.diy on Fly.io

The site (on Vercel) embeds the booking system from a self-hosted [Cal.diy](https://github.com/calcom/cal.diy), the MIT community fork of Cal.com. Visitors only ever see it inside the site's booking pages. It runs on Fly.io, in the `personal` organisation, region `ams` (Amsterdam; the cheapest EU region on Fly).

| Fly app | Config | What it does |
|---|---|---|
| `rusc-cal` | `fly.toml` | Cal.diy at https://rusc-cal.fly.dev (later https://booking.studio-rusc.com). One machine, shared CPU, 2 GB. It applies database migrations when it starts, and runs `cron.sh` (Cal.diy's background tasks: email queue, calendar sync, cleanups) beside the server. |
| `rusc-cal-db` | `fly.db.toml` | PostgreSQL 16 on a 1 GB volume, 512 MB machine. Only reachable from `rusc-cal`, over Fly's private network. Fly snapshots the volume daily and keeps 14 days. |

The Cal.diy image is `ghcr.io/mohamedfekryyy/rusc-cal:<tag>`. It is built by `.github/workflows/cal-image.yml` from the `calcom/cal.diy` commit in `CAL_DIY_REF` and is public (it holds no secrets).

**Secrets** are Fly secrets only, generated by `setup.sh` and never printed: `fly secrets list -a rusc-cal` shows their names.

**Cost:** about $15 a month (2 GB machine ≈ $11, database ≈ $3.30, volume $0.15; HTTPS certificates and a shared IPv4 are free). If Fly's metrics show the Cal.diy machine well under 1 GB, `fly scale memory 1024 -a rusc-cal` brings it to about $9.50.

## First setup

1. **Fly.** Log in on this machine (`fly auth login`), then from this folder run `sh setup.sh`. It:
   - creates the two apps;
   - generates the secrets;
   - deploys the database, then Cal.diy (the first start takes a few minutes);
   - closes public sign-up by turning on Cal.diy's `disable-signup` flag.

   `setup.sh` is safe to run again.
2. **Right away**, open https://rusc-cal.fly.dev/auth/setup and create the studio's admin account. Cal.diy only allows this while no account exists.
3. **In Cal.diy:**
   - Choose the username, and French as the language.
   - Create one event type per session and language, with the exact slugs `<key>-fr` and `<key>-en`. The sessions are the offers with `kind: "session"` in `lib/cal.ts`: `atelier-ceramique-2h`, `atelier-modelage-2h`, `decor-a-cru-1h`, `modelage-enfant`, `atelier-ceramique-1j`, `atelier-ceramique-2j`, `porcelaine`, `atelier-libre-1h`.
   - Turn on **Requires confirmation** and leave payments off. Visitors pay in the site's cart (Stripe), and the studio confirms the booking once it's paid.
   - Cards, membership and gift vouchers need no event type: they go straight into the cart.
4. **Emails (Brevo).**
   - Create an SMTP key (SMTP & API → SMTP).
   - Authenticate studio-rusc.com (Senders & domains) with the DNS records Brevo gives, at Squarespace. Without them, booking emails land in spam.
   - Then run this yourself, so the key never leaves your terminal:
     ```bash
     fly secrets set -a rusc-cal EMAIL_SERVER_USER=<Brevo SMTP login> EMAIL_SERVER_PASSWORD=<Brevo SMTP key>
     ```
5. **Own domain** (optional; can wait):
   - Run `fly certs add booking.studio-rusc.com -a rusc-cal`.
   - In Squarespace Domains → studio-rusc.com → DNS, add the records it prints: a `CNAME` for `booking` → `rusc-cal.fly.dev`.
   - Once `fly certs show booking.studio-rusc.com -a rusc-cal` says issued, change the two URLs at the top of `fly.toml` to `https://booking.studio-rusc.com` and run `sh deploy.sh`.
6. **Point the site at it.** In Vercel → `rusc-preview` → Settings → Environment Variables:
   - set `NEXT_PUBLIC_CAL_ORIGIN` to the address from step 2 or 5;
   - set `NEXT_PUBLIC_CAL_USERNAME` to the username from step 3;
   - redeploy.

## Updating Cal.diy

1. Put a newer `calcom/cal.diy` commit in `CAL_DIY_REF` and push. The workflow builds the new image (30–60 minutes).
2. Once it's green, back up the database (below), then from this folder run `sh deploy.sh`.

## Logs and status

```bash
fly status -a rusc-cal
fly logs -a rusc-cal        # or -a rusc-cal-db
fly ssh console -a rusc-cal-db -C "psql -U cal -d cal"
```

## Backups and restoring

- **Daily snapshots** of the database volume are kept 14 days:
  ```bash
  fly volumes list -a rusc-cal-db
  fly volumes snapshots list <volume id>
  ```
- **A dump on your computer** (do this before each update):
  ```bash
  fly ssh console -a rusc-cal-db -C "pg_dump -U cal cal" > cal-$(date +%F).sql
  ```
  Dumps contain client data: keep them out of this repo.
- **Restoring a snapshot:**
  1. Create a new volume from it: `fly volumes create pgdata --snapshot-id <snapshot id> -r ams -s 1 -a rusc-cal-db`.
  2. Destroy the database machine (`fly machine destroy <id> --force -a rusc-cal-db`) and the old volume, once you're sure. Destroying them is permanent.
  3. Run `fly deploy -c fly.db.toml --ha=false`, which mounts the restored volume.
